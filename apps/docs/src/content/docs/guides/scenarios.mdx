A scenario is an ordered list of steps. Each step flies a packet along your edges, or makes one node do something. A diagram can have as many scenarios as you like, and readers switch between them above the canvas.

## Steps

```yaml
scenarios:
  cache-miss:
    title: Browse a product (cache miss)
    summary: The product is not cached yet, so the catalogue reads PostgreSQL.
    phases:
      - title: The request
        steps:
          - browser -> catalog: GET /products/42
      - title: Cache miss
        steps:
          - catalog -> redis: { label: GET product:42, kind: lookup }
          - redis -> catalog: { label: miss, kind: error }
          - at catalog: { label: SET product:42 ttl 60s, note: The next request is a hit. }
```

| Step | Meaning |
|---|---|
| `a -> b: label` | A packet travels from `a` to `b`. |
| `at a: label` | Node `a` does something. It pulses and shows the caption. |
| `par: [ ... ]` | The steps inside start together. |

Steps use the edges you declared. If there is no direct edge, the packet takes the shortest route, hop by hop (`browser -> catalog` goes through the CDN and the gateway). Force a route with `via: [gateway]`. Flying **against** an edge makes the packet a response, so `redis -> catalog` over a `catalog -> redis` edge is drawn green without you saying so.

Options on a step: `label`, `kind` (`request`, `response`, `error`, `lookup`, `event`), `note` (markdown shown in the step list), `status` (`planned` draws it dashed) and `hold` (extra seconds to pause).

If you do not need phases, use a flat `steps:` list.

## Many scenarios

Short scenarios fit inside `diagram.yaml`. Longer ones can live in their own file. Every `diagrams/<name>/scenarios/<id>.yaml` becomes a scenario with that id:

```yaml
# diagrams/platform/scenarios/device-offline.yaml
title: Device is offline
phases:
  - title: Dispatch
    steps:
      - backend -> control-api: enqueue job
```

A scenario plays on the first view unless it sets `view:`. Every node it mentions must be in that view.

## Story view

The same scenario can be read as a **story**: swimlanes, with one column per actor, the steps running down the page in order, and the phases as horizontal bands. It is the version to put in front of someone who has not seen the system before.

<Diagram name="platform" scenario="request-story" />

Every step becomes a box in the lane where it happens:

| Step | In the story |
|---|---|
| `at a: ...` | A box in `a`'s lane. |
| `a -> b: ...` | A box in `b`'s lane, joined to the box before it by an arrow. If the story is not already at `a`, a small box shows where it starts. |
| `a -> b: { kind: lookup }` | A dashed box beside the step that asked, in `b`'s lane, with a double-headed dotted arrow. The answer that follows (`b -> a: ...`) is folded into the same box. |

Boxes are numbered 1, 2, 3 along the story. Lookups are not numbered. Click a box to play that step.

Without any extra YAML you get a lane per node, in the order they first appear. To shape it, add three optional things:

```yaml
scenarios:
  request-story:
    title: One read request, end to end
    mode: story                 # open as a story (flow and sequence stay one click away)
    lanes:                      # columns, left to right
      - { title: Operator browser, nodes: [operator] }
      - { title: Management stores, sub: Redis · Postgres, nodes: [redis, postgres] }
      - { title: Network, sub: hub ⇒ tunnel ⇒ spoke, nodes: [hub, spoke] }
    phases:
      - title: Who, where, may they?
        caption: on the management side     # shown under the title in the gutter
        steps:
          - proxy -> backend:
              title: Who are you?            # the box heading (defaults to the label)
              detail: |                      # one to three short lines under it
                session cookie → session
                tokens read from Redis
          - backend -> redis: { label: session + tokens, kind: lookup }
          - redis -> backend: found
```

A lane can hold several nodes, which is how you show "the data stores" or "the network" as one column. List the lanes in the order you want them; nodes you leave out get a lane of their own at the end, and `pnpm check` tells you which. Steps without a `title` use their label, and without a `detail` show `from → to`.

To show a story in a page without the picker, pass `mode`: `<Diagram name="platform" scenario="request-story" mode="story" />`.

## What readers get

- **Play, pause, step** forwards and back, scrub the timeline, and change the speed.
- **Click a step** in the list to jump to it. The path already travelled stays lit.
- **Flow, Sequence or Story**: the same scenario as packets over the architecture, as a classic sequence diagram, or as swimlanes.
- **Deep links**: the address bar follows the scenario and step, so a reader can share exactly what they are looking at.
- Scenarios start paused when the system asks for reduced motion.
